# 开发、验证与发布工作流程

本文件承接 AGENTS.md 的详细流程。任务开始时先确认用户当前指令及已有授权，按任务需要核对 GitHub 与工作区；涉及业务或页面时阅读相应主题。用户本轮范围和授权优先，限定授权不能扩展到其他任务。


## 0. 开工前先确认

每次改动前先快速判断并在心里确认：

1. 本次是数据修正、后端接口、前端展示、架构重构、测试补强，还是运行部署。
2. 是否会触碰投资页、收支页、风控页的前端结构或样式。
3. 是否会改变事实表、分类口径、收益口径或风控口径。
4. 是否需要同步重建 `pams-web` 或 `pams-api`。
5. 是否需要新增回归测试防止同类问题复发。

若用户明确说“禁止动前端”或“固定当前前端”，只能改数据、后端服务、接口字段绑定或必要文案映射，不得改视觉设计、布局、导航结构。

## 0.1 开发阶段、验收基线与冻结规则

本节优先于后文一般提交、验证和部署习惯。开发进度与 PR 直接使用 GitHub 状态及关联记录；不得仅凭分支、测试成功或标签名判断线上运行或用户验收。不再维护本地开发状态文件。

### 基线与阶段

- `main` 是集成分支，不等于已验收稳定版。只有用户明确验收后，才可登记稳定基线、打 `stable/...` 标签。
- 阶段在 GitHub 既有状态树中表达，区分范围确认、开发、自测和用户验收；发现回退或验收失败应更新相关任务，暂停时记录原因，不在 Markdown 重复维护阶段。
- 测试通过、PR 合并、部署成功、数据核准、用户验收必须分别记录，禁止互相替代。旧 `verified`、`recovery` 标签只表示当时技术检查，不追认为用户验收。
- 没有可证明的用户验收时，不能自行挑选旧 commit 充当稳定版；标签、完整 commit、验收日期与依据关联对应 PR/发布记录。
- GitHub 是开发进度的唯一来源；部署记录归对应功能 PR，实际运行以带时间机器观察核对。开发结论、测试、必要决策和异常归对应 PR，未提交的本地工作在回复中交接，不维护本地过程报告；审计报告不产生新资产事实来源。

### 记录归属与交接

| 内容 | 唯一维护位置 |
| --- | --- |
| 任务阶段、PR、提交 | GitHub 既有状态树及关联 PR/检查；正文引用即可，不复制进度列表 |
| 当前允许范围、暂停、提交/部署许可 | 用户当前指令和可追溯授权记录；仓库长期规则见 AGENTS |
| 发布时刻、各服务镜像/来源、配置/schema、验证、回退点、风险 | 对应功能 PR 的中文部署评论，原机器观察及私有证据链接 |
| 实际运行 | 带观察时间的机器报告；旧 GitHub 评论与归档仅代表当时，不当实时绿灯 |
| 验收、财务核准、备份及恢复证据 | 对应 PR/部署/专项证据，分别记录；不从测试结果或上线推断 |
| 尚未提交的本地工作 | 本轮回复交接范围、变更、验证和未决项，遵守用户不提交要求 |

跨 worktree 明确原工作区、当前检出与发布工作区差异，保护并行修改；只同步有效规则及其依赖，不强制同步开发进度。已完成能力的保留依据和回退候选仍须可追溯，候选不等于执行授权。

### 开发和发布门禁

1. 修改前列明要改什么、不改什么，以及需要保留的既有功能；按受影响范围保存必要底稿。
2. 核对原工作区（含未提交和未跟踪文件）及分支/main，涉及运行或发布时再核对实际镜像。三者不一致时先做差异清单，禁止把干净检出直接当作完整产品覆盖上线。
3. 只实施本轮已确认范围。新增功能与修复分开；不能顺带删除旧入口、收敛历史 PR、改变默认配置或改收益/NAV 口径。
4. 自测必须覆盖新行为及既有功能保留。记录失败项、未测试项和前后数值差异，不以增加测试数量证明没有回退。
5. PR 创建/推送与合并、部署分开。未经用户明确授权当前范围，不自动合并或发布；测试和构建不代表授权生产部署。
6. 涉及页面、金额、收益、NAV 的变化先说明差异、来源与风险，交用户验收。未验收不得登记完成或提升稳定基线。
7. 用户说“先暂停”“只盘点”“不要改代码/部署”时，仅做获准的文档更新和只读审计；不得修代码、写业务数据、建表、运行刷新、重启服务、重建/切换生产镜像或执行回退。文档修改不要求生产重建。

### 分层回退

- 代码回退：限定本轮相关提交，保留用户和其他任务的修改，不使用破坏性 reset。
- 部署回退：显式匹配 API、web、scheduler 镜像和配置；先检查 schema/API 兼容及缓存，用户确认后执行。
- 数据恢复：与代码回退独立审批，不能为恢复旧版本自动回灌数据库覆盖后续交易。备份必须记录时间、范围、校验和与恢复验证状态；未完成备份不能登记可恢复。
- 原始文件未删除、事实表校验未变，并不等于显示口径未变或资产可信；两类结论必须分开。

## 0.2 单人开发的本地验证

GitHub CI 保持关闭，合并时无需等待 `verify` 或申请跳过 CI。按本次改动选择下面适用的检查。多个账户共用同一规则时，在共用模型上验证一次，有业务差异才增加样例。

| 改动 | 本地怎么验 |
| --- | --- |
| 纯文档 | 核对规则、引用和差异格式。 |
| 文案、样式、布局 | 在受影响页面检查显示效果。公共布局改动覆盖受影响模板及手机、宽屏视口。 |
| 交互、筛选、缓存 | 从用户入口实际走一遍。例如修改流水分类后，核对列表位置和汇总是否更新。 |
| 收益、估值、划转、负债 | 用已知输入核对受影响的金额、日期和归属。例如只补行情时份额不变，市值随价格更新；跨年清仓分别核对累计收益和本年收益。 |
| 导入、事实写入、数据库升级 | 用显式隔离库走实际写入路径。按改动核对事务、升级兼容性及幂等性，例如同一资料导入两次后，交易笔数和余额只受一次影响。 |

**何时留下自动测试。** 只有关键财务口径发生变化，或实际出现的 bug 值得防止复发时，才补必要用例。优先扩展能覆盖该行为的现有用例。修 bug 时用最小输入复现旧错误，再验证修复后的预期结果。重复入账、划转双边扣减、跨年收益是相关改动的例子，无须提前建套件或补历史覆盖率。

**从提交到上线。** 在 PR 写清改了什么、验证了哪个场景、期望和实际结果，以及失败或未测项。最终提交的相关源码、依赖和构建输入一致时可复用验证结果；出现冲突或输入变化就重验受影响部分。获准部署时只切换受影响组件，核对镜像、配置和回退点。上线后从用户入口核对一个具体业务结果，例如已配对的投资入金从消费移出且现金净变化保持一致。

**财务核对。** 核对前后使用相同账户、业务日期、币种和归属。共享模型变动影响多个汇总时，沿调用方扩大核对范围。线上核对只读；如果对不上，记录差额和来源，停止后续发布。迁移、回填和数据恢复仍分别取得授权。

## 限定授权的使用

具体授权以用户原始指令及对应 GitHub 记录核对，旧授权不自动扩展到其他功能、日期、迁移或修账。长期证据、身份和恢复要求见 [修复、发布与恢复](REPAIR_RELEASE_AND_RECOVERY.md)。

## 1. 变更分级与 GitHub 同步

本节是长期记忆规则，优先级高于普通工作习惯。每次涉及代码、文档、数据脚本、测试或配置的修改，结束前都必须主动自检：是否已分级、是否已验证、是否已提交、是否已推送、是否已通过中文 PR 或中文 PR 评论记录。不能因为上下文压缩、切换任务或工作区脏状态而跳过。

每次代码或文档改动都必须先按影响范围分级，并在结论里说明本轮属于哪一级。分级用于决定验证范围、提交粒度和 PR 粒度。

变更分级：

- **S 级：低风险小改动**。只改文案、README、注释、字段展示映射、单点样式微调、单个接口的小修小补。按第 0.2 节做文档、页面或接口的定向验证。
- **M 级：中等改动**。修改一个明确模块的业务逻辑、接口返回、数据口径、前端组件交互、同步任务或一组同源 bug。验证受影响的用户路径或业务结果。
- **L 级：高影响改动**。新增页面、新增功能、事实表 / schema 变化、收益 / NAV / 风险 / 配置口径变化、跨页面联动、架构重构或数据迁移。按影响范围核对调用方和运行结果；是否新增自动测试按第 0.2 节判断。

GitHub 同步规则：

- **所有改动都要同步到 GitHub**。不能只停留在本地工作区，除非用户明确要求暂不提交。
- 每次同步都必须通过 PR，PR 标题和正文必须使用中文，说明改动范围、变更分级、验证结果和剩余风险。
- 新增功能、新增页面、schema 变更、口径变更、跨页面联动等 **L 级改动必须单独对应一条 PR**，不能和无关 bug 或样式调整混在一起。
- bug 修复可以按同一模块、同一根因或同一页面合并成一条 PR；不同根因、不同口径的 bug 不要强行塞进同一 PR。
- 纯文档改动可以单独提交一条文档 PR，但部署记录适用下面的专门规则；功能变更的必要文档跟随该功能 PR。
- **部署记录不得单独新建 PR**。必须在对应功能/修复 PR 下追加中文评论，即使该 PR 已合并；说明部署时间、源码 commit、各服务镜像版本、实际更新范围、验证结果、回退点及剩余风险。
- 部署后更新对应功能 PR 评论与同一机器观察的归档状态；不创建本地状态或过程报告副本。必要决策/异常归对应 PR，相关业务文档随下一条相关 PR 归入，不为部署记录另开 PR、不直推 main 或自动合并。
- 用户要求关闭独立部署记录 PR 时，先将完整部署记录迁到原功能/修复 PR 评论，再关闭记录 PR；关闭不等于合并，其文档提交须保留，待下一条相关 PR 归并。
- 工作区存在历史脏状态时，必须显式暂存本轮相关文件，禁止 `git add .` 把无关文件、缓存、报表、Excel 或旧实验结果带进提交。
- PR 合并后要确认 `origin/main` 已更新；若无法合并，要明确说明阻塞原因和下一步。

## 3. 运行态注意事项

当前 `compose.yaml` 下的 `pams-web` 是构建镜像，不是挂载本地 `frontend/public`。

因此：

- 改前端静态文件后，仅修改本地文件不会让 `http://pams.local` 立刻生效。
- 获部署授权后，才按受影响范围构建/切换 `pams-web`；已有通过验证的同一候选镜像可复用，不默认重建。
- 改 API Python 代码后先验证候选构建；获部署授权后才更新 `pams-api`，不能据此连带重建无关服务。
- 若只是查数据库或改数据，不要无意义重建容器。
- Web 构建在生成手机样式后按静态资源内容生成版本目录，并更新发布产物的 HTML 引用。源码使用相对路径。

本地语法检查和容器状态命令见[提交前最小验收](#11-提交前最小验收)。部署后按[发布身份](REPAIR_RELEASE_AND_RECOVERY.md#发布身份)核验并记录到原功能 PR。

## 9. 后端改动原则

- 图表组件不负责业务分类。
- 分类规则集中在服务层或资产底表，不散落在前端。
- 新增字段必须向后兼容。
- 不在 endpoint 里写运行时 DDL；表结构变更应走 `database/postgres/schema`。
- API read adapter 按领域放在 `backend/api/domain/`，endpoint 只做参数和响应封装。

## 10. 页面验证方法

生产页面以 `http://pams.local` 为准，候选验证不能代替部署后的线上核验。先按第 0.2 节确定范围；以下为可选的页面核对示例，按改动选择适用项：

- 投资页能打开。
- 交易明细能加载。
- 分析页的持仓穿透 / 收益归因切换正常。
- 风控页不超时。
- 页面没有恢复已删除的旧 UI。
- 关键文案没有英文原始枚举泄漏，例如 `deposit`。

如果用 PowerShell 拉 API，中文输出可能乱码；判断数据库中文是否正确时优先用 `psql` UTF-8 管道或浏览器页面实际渲染。

## 11. 提交前最小验收

先按第 0.2 节选择必跑、抽样和可复用证据。纯文档只做静态核对；以下是相关模块命令示例，不要求每轮逐条执行，也不代替最终提交验证：

```powershell
node --check frontend\public\assets\js\transactions.js
```

以下构建/运行命令仅适用于已获部署授权的受影响服务，不能当作每轮必跑清单；须使用已核准发布源码和原配置，不能直接用原脏工作区覆盖运行环境。已有经验证候选时优先复用同一镜像，不重建无关组件：

```powershell
docker compose up -d --build pams-web
docker compose up -d --build pams-api
docker ps --filter "name=pams-web" --filter "name=pams-api"
```

不要把无关脏状态、旧实验文件、压缩包、缓存目录混进本次结论。工作区已存在大量历史未跟踪文件，提交或汇总时必须只列本轮相关文件。
